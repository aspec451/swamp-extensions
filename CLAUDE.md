# Project: swamp-extensions

Extensions for [swamp](https://github.com/swamp-club/swamp), published under the
`@aspec451` collective.

## Extension Structure

Each extension is a self-contained swamp repository in its own directory:

```
<vendor>/<extension>/
├── manifest.yaml       # registry metadata
├── .swamp.yaml         # swamp repo marker (created by `swamp repo init`)
├── deno.json           # check / lint / fmt / fmt:check / test tasks
├── README.md           # per-extension docs (shipped via additionalFiles)
├── LICENSE.md          # Apache-2.0 (shipped via additionalFiles)
└── extensions/
    ├── models/         # export const model
    └── reports/        # export const report
```

Per-extension `CLAUDE.md`, `AGENTS.md`, and `.claude/` are generated by
`swamp repo init` and are **gitignored** — this root file is the single source
of project guidance.

## Manifest Format

```yaml
manifestVersion: 1
name: "@aspec451/<vendor>/<extension>"
version: "YYYY.MM.DD.N"
description: "One line, no trailing period"
repository: "https://github.com/aspec451/swamp-extensions"
models:
  - <vendor>/<file>.ts        # paths relative to extensions/models/
additionalFiles:
  - README.md
  - LICENSE.md
platforms:
  - linux-x86_64
  - linux-aarch64
  - darwin-x86_64
  - darwin-aarch64
labels: [...]
```

## Naming Conventions

- Type: `@aspec451/<vendor>/<extension>`, lowercase, hyphens.
- Directory matches the type minus the collective: `microsoft/sharepoint-lists`.
- Model source file uses snake_case: `sharepoint_lists.ts`.
- Shared helpers live in `_lib/` beside the model, prefixed `_` so swamp's
  discovery skips them (they carry no `export const model`).

## Licensing

Every `LICENSE.md` is Apache-2.0 with exactly one copyright line:

```
Copyright 2026 aspec451
```

When adapting code from another Apache-2.0 project, keep its attribution and
state the changes in the file header — Apache-2.0 §4(b). See
`microsoft/sharepoint-lists/extensions/models/microsoft/_lib/auth.ts`.

## Dependency Import Specifiers (HARD RULE)

Shipped source must use inline, pinned specifiers:

```ts
import { z } from "npm:zod@4";   // correct
import { z } from "zod";         // WRONG — publishes but scores UNSCORED
```

The registry quality scorer runs in a hermetic sandbox that strips the repo's
`deno.json` and writes its own with no imports map, so bare specifiers resolve
locally and fail at score time. `deno check`, `lint` and `test` all pass with
bare imports, so CI is the only place this gets caught.

Keep the zod pin identical across every extension.

## Model Rules

- Declare `type:` as a **string literal**, never a constant reference — swamp's
  static extractor reads the export block textually and warns
  `type field could not be extracted` otherwise. A named constant is fine for
  `collectedBy` fields.
- Schemas are plain `z.object`; no `.passthrough()` / `.loose()` (it breaks CEL
  expression validation).
- Mark credential fields `.meta({ sensitive: true })`.
- Every resource/file spec declares both `lifetime` and `garbageCollection`.
- Any method that paginates or caps results must expose a `truncated` boolean in
  its output spec and set it honestly.
- Bumping a model's `version` requires an `upgrades` entry — without one,
  existing instances stay pinned to their old `typeVersion` forever.

## Testing Rules

Tests are colocated as `*_test.ts` and excluded from discovery and publish.
Use `@systeminit/swamp-testing`:

- `createModelTestContext({ globalArgs, storedResources })` for method execution
- `withMockedFetch` for anything calling an external API
- `getWrittenResources()` to assert on what was written

Cover failure paths, not just success: API errors, invalid input, missing
resources, truncation.

## Commands

```bash
cd <vendor>/<extension>

deno task check | lint | fmt | fmt:check | test

swamp model type search <query> --json
swamp doctor extensions --json          # denoPath, load errors
swamp extension fmt manifest.yaml --check
swamp extension version --manifest manifest.yaml --json
swamp extension quality manifest.yaml --json
swamp extension push manifest.yaml --dry-run
```

Swamp bundles Deno at `~/.swamp/deno/deno` (not on `PATH`).

## Versioning

`YYYY.MM.DD.N` — date of publish plus a same-day counter.
`swamp extension version --manifest manifest.yaml --json` computes the next one.

## Publishing

The publish path is a state machine; each state gates the next:

```
repo_verified → auth_verified → manifest_validated → versioned
  → formatted → quality_checked → dry_run_passed → pushed
```

**Adversarial review happens before the push, not in the repo.** `swamp
extension push` warns and prompts unless a content-hash-bound review report
exists on disk. This repo does not commit those reports — review is a step you
perform and present, and `--yes` accepts the prompt.

1. Review the code against every dimension the dry-run skeleton lists.
   `swamp extension push manifest.yaml --dry-run --json` prints that skeleton
   with every applicable dimension set to `"pending"`.
2. Present findings for every dimension — `pass`, `issue` (say what and where)
   or `na`. Leave nothing unexamined.
3. Publish only after explicit confirmation.

A review goes stale the moment the code moves: any source edit or version bump
means re-reviewing before publishing. The archive hash covers `additionalFiles`
too, so editing `README.md` or `LICENSE.md` counts as a change just as editing a
model does.

`.github/workflows/publish.yml` passes `--yes` so CI needs no report on disk,
and `.extension-reviews/` is gitignored — a report written by a local
`--dry-run` stays local.

This follows webframp/swamp-extensions, and the trade-off is deliberate: swamp's
own gate binds a report to the exact archive hash, so what was reviewed is
provably what ships. Dropping it moves that guarantee from the tool to the
process — nothing mechanically verifies at push time that a review happened.

**Do not publish automatically.** Present the summary and wait for explicit
confirmation.

## Published-Surface Hygiene

`README.md`, `additionalFiles`, and test fixtures must use placeholders, never
real infrastructure identifiers. Check for real account IDs, tenant IDs, client
IDs, internal hostnames, site names, IPs and CIDRs — including values inherited
from whatever extension the code was adapted from. Use `contoso.sharepoint.com`,
`example.com`, RFC 5737 IPs, and obviously-synthetic GUIDs.

**Tenant IDs and client IDs are both placeholders.** Neither is a secret on its
own — a tenant ID is resolvable from any tenant domain via
`https://login.microsoftonline.com/<domain>/v2.0/.well-known/openid-configuration`,
and a public-client registration has no client secret. But a real tenant ID plus
a real client ID plus the scopes is the complete input to a device-code
authorization request against that registration, which is the ingredient list
for device-code phishing. Publishing neither half keeps the pair out of reach,
and costs a reader one substitution.

Current placeholders: tenant `aaaaaaaa-bbbb-cccc-dddd-eeeeeeeeeeee`, client
`11111111-2222-3333-4444-555555555555`.
